# Windows x86-64 baseline — 2026-09-13

This is the first reconnaissance baseline for the component-owned benchmark suite. The source tree was based on parent
commit `e458912b5c96e9e9bde16e850d6f0ac01b4e7ed9`; the benchmark harness itself is the change documented by this result.

## Environment

- Windows 11 Pro 10.0.26200, build 26200
- Intel Core i5-3210M at 2.50 GHz, 2 cores / 4 logical processors
- 8 GB physical memory
- ClangCL/LLVM 22.1.8, C++20, Bazel `-c opt`
- Google Benchmark 1.9.5
- GHC 9.10.3, Cabal 3.16.1.0, `-O2`
- Criterion 1.6.5.0

The machine was not frequency-pinned. Results are suitable for locating scaling problems and establishing the suite, not
for claiming cross-machine throughput. Google Benchmark used `--benchmark_min_time=0.05s`; Criterion used
`-L 0.1 --resamples 100`, with the noisy 512-function CorePrep decode repeated at `-L 1 --resamples 500`.

## Initial findings

The benchmark suite immediately exposes two performance directions worth profiling. Native Core verification, Xpp/Xmm
verification, Xpp/Xmm optimization, and Xpp/Xmm encoding fit quadratic growth on these fixtures. Haskell CorePrep and wire
operations also grow faster than their smallest cases predict. These are observations, not correctness failures and not
yet regression thresholds. The next optimization work should profile repeated linear searches and list concatenation in
the relevant verifier, optimizer, and encoder loops, then retain this input family as the before/after comparison.
